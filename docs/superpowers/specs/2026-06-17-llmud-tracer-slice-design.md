# 修仙 LLM MUD —— 穿透式切片（Tracer-Bullet Slice）设计文档

> 日期：2026-06-17
> 项目：`llmud`（LLM 驱动的修仙 MUD）
> 本文档范围：**第一个子项目**——穿透式垂直切片。它不是完整产品设计，而是验证“核心循环 + 陪伴钩子”的最小可玩骨架。完整产品被拆分为多个子项目，本文档只覆盖第一个，其余子项目各自有独立的 spec → plan → 实现周期。

> 约定：所有存储字段与 JSON 契约键名使用英文（与现有 `main.py` 的 `PLAYER_DB` 一致）；中文仅用于 UI 展示与本文档描述。

---

## 1. 背景与上下文

### 1.1 项目现状

`llmud` 当前是一个早期原型，共三个文件：

- `main.py`：FastAPI 后端，调用 DeepSeek 充当“动态地下城主（DM）”。用一个内存字典维护**单个硬编码玩家**（name=张铁柱 / location=青云门外门柴房 / level=练气期一层 / spirit_power=10）。每次行动把玩家状态拼进 system prompt，要求模型返回 JSON（`story` / `new_location` / `spirit_change`），正则提取后更新地点与灵力，再把 `story` 以 `StreamingResponse` 假流式返回。
- `index.html`：仿微信聊天的 H5 前端。顶部状态栏（地点/境界/灵力）从 `/player/status` 拉取；聊天区渲染气泡；输入栏 POST 到 `/game/action`，读流、尝试 `JSON.parse` 后只展示 `story`，再刷新状态。
- `你知道MUD游戏吗？.txt`：一份产品构想对话记录，论证了“AI 负责皮、代码负责骨”的架构，以及面向中国市场以“高浓度情感陪伴/社交”为赢面的结论，落地形态为“服务号作入口 + H5 网页承载游戏”。

已知问题（本切片需顺带修正）：

- `main.py` 把“状态引擎 / LLM 叙事 / NPC 记忆 / API 编排”四件事揉进一个函数，边界模糊，无法独立测试与演进。
- API Key 硬编码在源码中（`sk-684b...`），已随文件落盘，属于安全隐患；切片期需移至环境变量，并建议轮换该 Key。
- 模型名 `deepseek-v4-flash` 疑似非 DeepSeek 有效模型 ID，需核实替换。

### 1.2 三项基础决策（已在头脑风暴阶段确认）

1. **核心体验 = 混合型**：修仙成长（境界/战斗/突破）为脊柱，NPC 情感陪伴为并列第二支柱，陪伴驱动留存与大部分变现。
2. **社交模型 = 单机 + 异步社交元层**：每个玩家拥有私密的修仙世界与 AI NPC，无实时多人共存；社交/传播通过排行榜、可分享战报/截图、互访 NPC 档案、UGC 等异步方式实现。
3. **目标定位 = 先验证的 MVP**：先做出可玩、可测留存的 MVP，验证核心循环与陪伴钩子，再叠加平台与变现。

### 1.3 为何选择“穿透式切片优先”（构建顺序 B）

完整产品被拆为以下独立子项目：

- **MVP 核心**（验证循环 + 钩子）：A 状态引擎、B LLM 叙事层 + 指令理解、C NPC 系统 + 记忆、D H5 前端 + 后端会话。
- **验证后**（规模化与变现）：E 世界模型与动态事件、F 异步社交元层、G 平台/运营（鉴权/支付/合规/扩容/监控）。

构建顺序有三种思路：A 逐层夯实（先做满状态引擎再做叙事……）、B 穿透式切片优先、C 陪伴支柱优先。已确认采用 **B**：在现有原型基础上扩展出一条最小端到端骨架（真·状态 + JSON DM 契约 + 一个有持久记忆与好感度的 NPC + H5 可玩），先端到端验证“循环 + 陪伴钩子”，再把 A/B/C/D 各自做深。理由：与“先验证 MVP”定位一致，能在投入加深任一层之前对整体体验去风险；现有原型本就是一条半成品的穿透切片，浪费极少。

## 2. 目标与成功标准

### 2.1 目标

一个可玩的端到端骨架，在加深任何一层之前证明两件事：

- **循环成立**：玩家行动 → 引擎确定性结算 → LLM 把结果叙述成爽文 → 状态更新 → 前端渲染，体验令人有获得感。
- **陪伴钩子成立**：一个 NPC 跨会话记住玩家，好感度随互动变化，有 persona/secret/motive，且绝不破壁（不承认自己是 AI），体验上“像一个人”。

### 2.2 成功标准

玩家在一次游玩中能够：

1. 修炼并获得灵力（验证成长循环）；
2. 与师姐对话，感受到“她记得我”（验证陪伴钩子）；
3. 与一只妖兽战斗，获得一段史诗化叙事 + 战报卡（验证战斗即叙事）；
4. 离开后再次进入，师姐能回忆起之前的对话内容（验证跨会话记忆）。

## 3. 范围：纳入与排除

### 3.1 纳入（IN）

- 一个持久化玩家（SQLite）。
- 一套小而真的属性集与确定性规则。
- 一个 NPC（师姐），含持久化记忆与好感度。
- 严格的 JSON DM 契约。
- 指令理解：规则优先 + LLM 兜底分类。
- 一次妖兽战斗（战斗即叙事）。
- 最小关键词级内容安全过滤。
- 演进后的 H5 前端：状态栏 + 战报卡 + 好感度指示。
- SQLite 持久化。

### 3.2 排除（OUT，刻意的“瘦身”，每项映射到后续子项目）

- 向量 RAG 库 → 延后至加深 C。
- 多 NPC、世界/地图、动态事件、解谜 → 子项目 E。
- 异步社交元层 → 子项目 F。
- 鉴权/登录、支付 → 子项目 G。
- 真正的逐字 token 流式 → 延后至加深 B。
- 深度战斗与掉落系统 → 延后至加深 A。

## 4. 架构：四层模块 + 三阶段数据流

把现有 `main.py` 重构为四个边界清晰的模块，每个模块都有明确接口，可被独立加深而不必连带改写其它层。

### 4.1 `engine/`（状态引擎，即“骨”）

- **职责**：纯函数。输入“当前状态 + 已解析的行动”，输出“新状态 + 数值变化”。
- **约束**：无 I/O、无 LLM 调用。完全可单元测试。
- **内容**：修炼增益规则（每次修炼 `spirit_power` +1~3，可配）、突破阈值与境界倍率表、派生属性（`attack = spirit_power × level_multiplier`、`defense = floor(spirit_power / 2) + 5`）、战斗伤害公式、胜负/逃跑判定、物品栏变更、位置移动。

### 4.2 `dm/`（LLM 叙事层，即“皮”）

- **职责**：拼装 prompt（引擎状态 + NPC 记忆 + 玩家行动）→ 经由薄而 provider 无关的 `LLMClient` 接口调用 LLM → 校验并解析 JSON 契约 → 返回解析后的契约字段（`story`、`state_delta`、`combat`、`breakthrough`、`npc_update` 等）。
- **默认 provider**：DeepSeek（已接线），通过 `LLMClient` 接口隔离，后续可换。
- **职责边界**：只产出“文字”，不产出战斗数值（数值由引擎给）。

### 4.3 `npc/`（陪伴支柱）

- **职责**：加载/保存唯一 NPC 的档案 + 记忆（近期轮次、前情提要、关键事实、好感度）；每次互动后更新；在 prompt 中强制“非 AI”护栏。

### 4.4 `api/`（FastAPI 服务）

- **职责**：端点编排 classify → engine → dm → npc；持久化到 SQLite；把结果返回前端。
- **附带修正**：把硬编码 API Key 移到环境变量。

### 4.5 一次行动的数据流（三阶段）

```
POST /game/action {player_id, action_text}
  ① 指令理解（classify）：规则/正则优先匹配四类原型（修炼/对话/战斗/移动），
     未命中则 LLM 兜底分类 → intent ∈ {cultivate,talk,fight,move,other} + 解析参数
  ② 引擎结算（engine，确定性、无 LLM）：按 intent 计算 state_delta / 战斗结果
     （combat：算出 dmg_to_enemy / dmg_to_player / result；other：仅做合法性轻校验）
  ③ 叙事（narrate，单次 LLM 调用）：以引擎数值为参数生成爽文，产出完整 JSON 契约
  → 解析 JSON → state_delta 应用到玩家、npc_update 应用到 NPC 记忆 → 持久化
  → 返回 story + 新状态
```

**铁律**：可确定性结算的数值（尤其战斗）由引擎在 ② 产出，叙事在 ③ 只能引用这些数值，不得臆造；对 `other` 自由行动，DM 可提议轻微 `state_delta`，引擎做合法性校验/钳制后生效。

## 5. 数据模型（SQLite 持久化）

### 5.1 Player

| 字段 | 类型 | 说明 |
|------|------|------|
| `id` | str | 玩家 ID（切片期可固定单玩家） |
| `name` | str | 姓名 |
| `level` | str | 境界，如“练气期一层” |
| `spirit_power` | int | 灵力 |
| `hp` / `max_hp` | int | 当前/最大气血 |
| `affinity` | str | 灵根属性 |
| `location` | str | 当前地点标签 |
| `inventory` | list | 物品栏 |
| `attack` | int（派生） | `spirit_power × level_multiplier` |
| `defense` | int（派生） | `floor(spirit_power / 2) + 5` |
| `created_at` / `last_seen` | datetime | 创建/最近活跃 |

### 5.2 NPC（师姐）

| 字段 | 类型 | 说明 |
|------|------|------|
| `id` | str | NPC ID |
| `name` | str | 姓名（如“林婉儿”，可调） |
| `persona` | str | 人设/性格 |
| `secret` | str | 隐藏信息，用于埋设未来大事件 |
| `motive` | str | 行为动机 |
| `system_prompt` | str | 由 persona/secret/motive 渲染而成 |
| `favorability` | int | 好感度 0–100 |
| `recent_turns` | list | 最近约 6 轮对话 |
| `summary` | str | 前情提要（AI 维护的摘要） |
| `key_facts` | list | `[{fact, turn}]`，按近因取前 5 条 |
| `relationship_stage` | str | 陌生→相识→熟悉→知己 |

### 5.3 Encounter

单个硬编码妖兽属性块（`attack` / `defense` / `hp`），用于战斗原型；本切片无地图，`location` 仅为可被 DM 改动的标签。

### 5.4 持久化接口

通过一层薄仓储接口（Repository）访问 SQLite，便于将来替换为 Postgres。

## 6. DM 契约（严格 JSON，禁止 markdown）

LLM 必须返回纯 JSON：

```json
{
  "intent": "cultivate|talk|fight|move|other",
  "action_valid": true,
  "invalid_reason": "",
  "story": "……（≤120 字爽文叙事）",
  "state_delta": { "spirit_power": 2, "hp": -5, "location": "……" },
  "breakthrough": null,
  "combat": null,
  "npc_update": null
}
```

- `breakthrough`：触发突破时为 `{"from":"…","to":"…"}`，否则 `null`。
- `combat`：战斗时为 `{"enemy":"妖兽","dmg_to_enemy":12,"dmg_to_player":5,"result":"win|lose|flee"}`，否则 `null`。
- `npc_update`：仅当 `intent=talk` 时存在，含 `{emotion, favorability_change, new_key_fact, summary_delta}`。

**指令理解（classify，阶段 ①）**：采用“规则优先 + LLM 兜底”——常见指令（修炼/打坐、去某地、攻击/砍某物、与某人说话）走规则/正则快速匹配，未命中时由一次轻量 LLM 调用兜底分类。命中规则时整条行动仅需 1 次 LLM 调用（叙事），同时保证引擎对数值的权威性；未命中时额外一次轻量分类调用。加深 B 时可进一步优化分类与流式。

**容错**：JSON 缺失或非法时，先用更严格的提示重试一次；仍失败则回退为直接展示原文，状态保持不变并记日志。

## 7. NPC 记忆架构（师姐）

### 7.1 每次对话的 prompt 上下文

```
system_prompt（persona/secret/motive + “你绝不是 AI”护栏）
+ summary（前情提要）
+ recent_turns（最近约 6 轮）
+ key_facts（按近因取前 5 条）
+ 当前玩家状态
+ 玩家本轮发言
```

### 7.2 每轮后的更新流程

1. 把本轮追加到 `recent_turns`。
2. 若有 `favorability_change`：更新 `favorability`，必要时推进 `relationship_stage`。
3. 若有 `new_key_fact`：存入 `key_facts`。
4. 当 `recent_turns` 累计超过 6 轮时：用一次廉价摘要调用，把近期轮次重写进 `summary` 并裁剪旧轮次。

### 7.3 护栏

- system prompt 写死：“你是修仙世界的活人，绝不是 AI/语言模型，绝不出戏。”
- 后置过滤：若模型自述为 AI，则改写为符合人设的拒答并记日志。

### 7.4 本切片不做向量 RAG

仅用“近期轮次 + 前情提要 + 关键事实”即可验证“她记得我”。向量 RAG 延后至加深 C。

## 8. 战斗即叙事

### 8.1 一次原型遭遇

固定属性的妖兽一只（`attack` / `defense` / `hp`）。

### 8.2 流程

玩家出手 → 引擎按简单公式结算：

- `dmg_to_enemy = max(1, player_attack - enemy_defense)`
- `dmg_to_player = max(1, enemy_attack - player_defense)`（仅当妖兽仍存活才反击）
- 扣血后判定 `result`：妖兽 hp ≤ 0 为 `win`，玩家 hp ≤ 0 为 `lose`，玩家主动撤退为 `flee`。

→ DM 收到数值与结果，必须据此生成史诗化战斗叙事并填好 `combat` 字段。引擎是 HP 与胜负的唯一真源；DM 不得臆造伤害。战斗结束后前端渲染战报卡（敌方、造成/受到伤害、结果、掉落若有）。

- 真正的多层、基于模型的合规体系属于子项目 G；本切片只需保证验证期间“不至于明显违规”。

## 11. 错误处理与测试

### 11.1 错误处理

- LLM/HTTP 错误：返回主题化文案（“传信飞鸽被雷劈了”），状态不变（原型已有此行为，保留）。
- JSON 解析失败：先严格重试一次，再回退展示原文，状态不变，记日志。
- 护栏命中：后置过滤改写为人设内拒答，记日志。

### 11.2 测试

- **状态引擎是可单元测试的核心**：修炼增益、突破阈值、派生属性、战斗伤害公式、胜负/逃跑、物品栏——均纯函数可测。
- DM/NPC 层：用**被 mock 的 `LLMClient`**（返回预设 JSON）做少量集成测试，验证编排逻辑（classify→engine→narrate→persist）而不消耗 token。

## 14. 待验证假设与风险

- **假设 1**：LLM 能稳定遵守 JSON 契约并拒绝臆造战斗数值。风险：模型“脑补”伤害。缓解：契约铁律 + 引擎是唯一真源 + 后置校验（若 `combat` 中的伤害与引擎算得不符，以引擎为准并记日志）。
- **假设 2**：“近期轮次 + 前情提要 + 关键事实”足以支撑跨会话“记得我”体验。风险：记忆仍显割裂。缓解：本切片即用来验证此项；若不足，提前引入轻量向量检索。
- **假设 3**：规则优先 + LLM 兜底的分类，在“任意离谱操作”的自由度与确定性结算之间取得平衡。风险：自由行动被错误归类。缓解：未命中走 LLM 兜底，`other` 意图由 DM 主导叙事、引擎仅轻校验。
- **假设 4**：DeepSeek 在中文修仙语境下的叙事质量与合规性足够。风险：合规或风格不达标。缓解：`LLMClient` 可替换；合规后置过滤兜底。
